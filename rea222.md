Да, при старте сделаем **неограниченное ожидание**, с интервалом 5 секунд. Это гарантирует как минимум 100 попыток; после сотой сервис продолжит ждать. Пока БД недоступна, воркер и scheduler не запускаются. При восстановлении приложение продолжает обычный старт.

Нюанс: `create_async_engine()` само по себе обычно ещё не подключается к БД. Поэтому ожидание нужно **явно поставить в `main.py` до `worker.run()` и `scheduler.start()`**. [Документация SQLAlchemy](https://docs.sqlalchemy.org/en/20/tutorial/engine.html).

В `connection.py` добавь функцию:

```python
import asyncio
import logging

logger = logging.getLogger(__name__)


async def wait_for_database() -> None:
    attempt = 0

    while True:
        attempt += 1

        try:
            async with engine.connect() as connection:
                await connection.execute(text("SELECT 1"))

            logger.info(
                "Подключение к PostgreSQL установлено после попытки %d",
                attempt,
            )
            return

        except (SQLAlchemyError, OSError, TimeoutError):
            # Не печатаем exc и traceback: в них могут быть
            # технические детали драйвера и адреса.
            logger.warning(
                "PostgreSQL пока недоступен; попытка %d. "
                "Повтор через 5 секунд",
                attempt,
            )
            await asyncio.sleep(5)
```

В `main.py` внутри `lifespan`, **до создания фоновой задачи воркера и запуска scheduler**:

```python
await wait_for_database()

worker_task = asyncio.create_task(
    worker.run(),
    name="analysis-worker",
)
scheduler.start()
```

Импорт:

```python
from app.database.connection import (
    get_database_engine,
    wait_for_database,
)
```

Ошибку подключения здесь мы перехватываем, поэтому стандартная трассировка SQLAlchemy при кратковременной недоступности из `lifespan` наружу не выйдет. `pool_pre_ping` эту задачу не заменяет: когда ни один хост недоступен, ошибка подключения всё равно передаётся вызывающему коду. [Документация SQLAlchemy](https://docs.sqlalchemy.org/en/20/core/pooling.html#disconnect-handling-pessimistic).

**Но у тебя до приложения запускается `alembic upgrade head`.** Если БД моргнёт именно в этот момент, `wait_for_database()` из приложения ещё не исполняется. Поэтому команду миграции на сервере тоже нужно запускать через отдельный цикл повторов: попытка `alembic upgrade head` → при временной ошибке подключения `WARNING` без текста исключения → пауза 5 секунд → новая попытка. Если миграция упала из-за неправильного SQL или схемы, её **нельзя** бесконечно повторять как ошибку соединения: такую ошибку нужно завершить и показать разработчику.

Я бы также не писал все 100 предупреждений в обычный лог: первое сразу, затем, например, каждую 12-ю попытку — раз в минуту. Состояние ожидания при этом должно быть видно через readiness. Если приложение работает в Kubernetes, его `startupProbe` нужно настроить так, чтобы длительное ожидание БД не приводило к перезапуску контейнера раньше времени. [Документация Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/probes/).

И последнее: **скрываем трассировки временных сбоев**, но не подавляем ошибки программирования и миграций. Иначе сервис может ждать бесконечно из-за неверной конфигурации, а в логах будет только «БД недоступна».
