# Проверка Analyzer и Dashboard

Тестовый API работает только при:

```env
TEST_DATA_API_ENABLED=true
```

В production ConfigMap значение должно быть `false`. Генератор не содержит отдельной dashboard-математики: он создаёт готовые `dialog_reports`, после чего вызывает обычный `DashboardBuilder`.

Перед генерацией удаляются только fixture-отчёты и dashboard-история выбранных менеджеров. Благодаря этому два тестовых сценария не смешиваются. Ручка предназначена только для изолированной тестовой среды.

## Создание истории

```http
POST /api/v1.0/ai-q-score/analysis/run/dashboard-test-data
```

```json
{
  "manager_ids": ["00000001", "00000002"],
  "date_from": "2026-10-01",
  "date_to": "2026-11-07",
  "dialogs_per_workday": 5,
  "scenario": "mixed",
  "metric_scores": {},
  "client_epk": "",
  "client_fio": ""
}
```

Менеджеры должны присутствовать в одном из четырёх ролевых ENV-списков. Выходные пропускаются. Диапазон ограничен 183 днями, число звонков — от 1 до 100 на менеджера за рабочий день.

## Сценарии

| Сценарий | Результат |
|---|---|
| `mixed` | Воспроизводимая смесь 0/1, вкладов и рисков |
| `happy_path` | Все применимые метрики выполнены, рисков нет |
| `no_deposit_topic` | `DEPOSIT_TOPIC=0`, депозитные метрики не влияют на UI и Q-score |
| `client_high_risk` | У клиента выявляются high-риски |
| `multiple_client_risks` | У одного клиента несколько разных рисков |
| `critical_violation` | Нарушается одна критичная Hygiene-метрика |
| `strengths_boundary_80` | `HYG_01` выполняется в 80% коммуникаций |
| `improvement_boundary_79` | `HYG_01` выполняется в 79% коммуникаций; рекомендуется создать 100 звонков |
| `no_dialogs` | Строятся нулевые/пустые dashboard snapshot без диалогов |

## Точные overrides

`metric_scores` имеет приоритет над сценарием:

```json
{
  "metric_scores": {
    "HYG_01": 0,
    "DEPOSIT_TOPIC": 1,
    "DEP_01": 0,
    "RISK_01": 0
  }
}
```

Разрешены только существующие коды и значения `0`/`1`. Если `DEPOSIT_TOPIC=0`, все остальные депозитные метрики детерминированно исключаются из аналитики независимо от overrides.

`client_epk` и `client_fio` позволяют заставить все сгенерированные звонки относиться к одному клиенту — это удобно для проверки агрегации нескольких рисков.

## Рекомендуемые проверки

1. Запустить `happy_path`, открыть Q-score, Strengths и список коммуникаций.
2. Запустить `no_deposit_topic`, убедиться, что `DEPOSIT_TOPIC` и депозитные нарушения нигде не появились.
3. Запустить `multiple_client_risks` с фиксированным EPK, проверить список клиентов и popup одного клиента.
4. Создать 100 звонков `strengths_boundary_80`, проверить граничное попадание в Strengths.
5. Создать 100 звонков `improvement_boundary_79`, проверить попадание в Improvements.
6. Проверить popup Improvement: четыре завершённые недели и не больше установленного лимита коммуникаций.
7. Запустить `no_dialogs`, проверить отсутствие `null` и наличие нулевых значений.
8. Проверить пагинацию седьмой GET-ручки через `limit`, `offset`, `hasMore`.

## Очистка и повторяемость

Call ID формируется детерминированно из сценария, менеджера, даты и номера звонка. Повторный запуск того же запроса обновляет fixture-отчёты, а не создаёт дубликаты. Тестовые данные подчиняются общему `DATA_TTL_DAYS`.
