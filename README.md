Нужно спроектировать production-ready механизм автоматического PostgreSQL failover для Python-приложения. Прошу внимательно проанализировать архитектуру, проверить технические утверждения и предложить конкретную реализацию, а не ограничиваться общими рекомендациями.

## 1. Текущий стек

- Python, asyncio.
- SQLAlchemy 2.0.51.
- asyncpg 0.31.0.
- PostgreSQL.
- Kubernetes, приложение работает в подах.
- PgBouncer, HAProxy и другие прокси использовать не планируется.
- Подключение должно осуществляться непосредственно к двум PostgreSQL-хостам.

Текущая архитектура:

- `get_database_engine()` создаёт `AsyncEngine` через `create_async_engine()`.
- `get_session_maker()` создаёт `async_sessionmaker`.
- Обе функции используют `@lru_cache`.
- `pool_size=10`.
- `max_overflow=20`.
- `pool_recycle=3600`.
- `pool_pre_ping=True`.
- `expire_on_commit=False`.
- `connect_args={"statement_cache_size": 0}`.

В конфигурации имеется логика `master_host_and_port`, которая выбирает один PostgreSQL-хост. Её необходимо заменить на multihost DSN, содержащий оба адреса.

## 2. Основная задача

Нужно обеспечить автоматическое переключение PostgreSQL Primary/Standby **во время работы приложения, без перезапуска пода, без ручного вмешательства и без изменения конфигурации**.

Необходимо поддержать два сценария.

**Сценарий A — отказ Primary:**

1. PostgreSQL-1 работает как Primary.
2. PostgreSQL-2 работает как Standby.
3. Приложение использует PostgreSQL-1.
4. PostgreSQL-1 становится недоступен.
5. Инфраструктура повышает PostgreSQL-2 до Primary.
6. Приложение автоматически восстанавливает соединения с PostgreSQL-2.

**Сценарий B — смена ролей при доступности обоих серверов:**

1. PostgreSQL-1 — Primary, PostgreSQL-2 — Standby.
2. SQLAlchemy держит соединения к PostgreSQL-1.
3. Происходит switchover.
4. PostgreSQL-1 становится Standby, PostgreSQL-2 — Primary.
5. Оба сервера продолжают отвечать.
6. Приложение должно обнаружить, что старые соединения больше не подходят для записи, и автоматически перейти на PostgreSQL-2.

Второй сценарий особенно важен: `pool_pre_ping=True` проверяет доступность соединения, но не гарантирует проверку роли PostgreSQL.

## 3. Предлагаемая конфигурация

Для SQLAlchemy + asyncpg предполагается multihost DSN следующего вида:

```python
DATABASE_URL = (
    "postgresql+asyncpg://user:password@/database"
    "?host=postgres-1:5432"
    "&host=postgres-2:5432"
)
```

И:

```python
connect_args={
    "target_session_attrs": "read-write",
    "statement_cache_size": 0,
    "timeout": 5,
}
```

Проверь корректность этой конфигурации именно для SQLAlchemy 2.0.51 и asyncpg 0.31.0.

Важно: asyncpg не использует libpq, в отличие от psycopg. Необходимо проверить поведение непосредственно asyncpg, не переносить автоматически свойства psycopg/libpq на этот драйвер.

## 4. Вопросы к архитектуре

**Первый: нужен ли отказ от `@lru_cache`?**

Сейчас `AsyncEngine` создаётся один раз и кэшируется.

Необходимо разобраться, действительно ли это мешает failover.

Моя предварительная гипотеза: `@lru_cache` можно оставить, потому что `AsyncEngine` управляет пулом физических соединений, а asyncpg заново выбирает хост при создании каждого нового физического соединения.

Прошу проверить это и не рекомендовать удаление кэширования без технического обоснования.

**Второй: как обнаруживать смену роли при живых соединениях?**

Рассмотреть проверку:

```sql
SELECT pg_is_in_recovery();
```

или:

```sql
SHOW transaction_read_only;
```

Нужно определить наиболее надёжный механизм проверки роли при checkout соединения из пула SQLAlchemy.

В частности, изучить использование SQLAlchemy PoolEvents:

- `checkout`;
- `invalidate`;
- `connect`.

Если соединение оказалось подключено к Standby, нужно добиться его корректной инвалидации и создания нового соединения через multihost DSN.

Рассмотреть `sqlalchemy.exc.DisconnectionError` внутри обработчика `checkout`, а также ограничение количества повторных попыток подключения.

Учесть, что SQLAlchemy AsyncEngine использует синхронную систему событий, поэтому нужно правильно организовать проверку роли, не нарушая асинхронную модель asyncpg.

**Третий: что делать с ошибками во время SQL-запроса?**

Если роль PostgreSQL изменилась уже после checkout, возможны ошибки:

- разрыв соединения;
- `ReadOnlySQLTransactionError`;
- SQLSTATE `25006`;
- ошибка во время `COMMIT`;
- ошибка соединения во время активной транзакции.

Нужно предложить обработку этих ситуаций с корректным закрытием старой `AsyncSession`, созданием новой и повтором операции там, где это безопасно.

Необходимо исключить бесконечные retry, некорректное повторное использование сломанной сессии и повторное выполнение неидемпотентных операций.

**Четвёртый: как инвалидировать старые соединения?**

Определить, когда достаточно стандартной инвалидации SQLAlchemy, а когда требуется:

```python
await engine.dispose()
```

Учитывать, что `dispose()` заменяет пул, но не закрывает принудительно все соединения, уже выданные активным сессиям.

Также рассмотреть конкурентную ситуацию: несколько запросов одновременно обнаруживают failover и пытаются пересоздать пул.

## 5. Production-требования

Нужно обеспечить:

1. Поддержку двух PostgreSQL-хостов в конфигурации YAML.
2. Выбор сервера, доступного для записи.
3. Автоматическое восстановление после полного отказа Primary.
4. Автоматическое обнаружение смены ролей при доступности обоих серверов.
5. Отсутствие необходимости перезапускать Kubernetes-поды.
6. Корректную работу пула соединений SQLAlchemy.
7. Ограниченные retry с backoff и jitter.
8. Корректную обработку активных транзакций.
9. Логирование failover и ошибок подключения.
10. Метрики для Prometheus, позволяющие обнаружить переключение и деградацию.
11. Защиту от повторного выполнения неидемпотентных операций.
12. Предсказуемое поведение при отсутствии доступного Primary.

Необходимо также объяснить, какие гарантии невозможно обеспечить исключительно средствами клиентского приложения, например прозрачное восстановление незавершённой транзакции или предотвращение потери подтверждённых данных при асинхронной репликации.

## 6. Локальное тестирование

Локально используются Podman и DBeaver.

Конфигурация:

Первый контейнер:

- Name: `ai-mentor-db`.
- User: `ai_mentor`.
- Password: `ai_mentor`.
- Database: `ai_mentor`.
- Port: `5432:5432`.

Второй контейнер:

- Name: `ai-mentor-db-2`.
- User: `ai_mentor`.
- Password: `ai_mentor`.
- Первоначально Database: `ai_mentor_2`.
- Port: `5433:5432`.

Учесть, что для физической репликации Standby должен содержать копию кластера Primary, включая базу `ai_mentor`. Независимые PostgreSQL-инстансы с разными данными не являются корректной имитацией HA-кластера.

Нужно предложить локальные тесты:

- Отключение Primary.
- Ручной promotion Standby.
- Switchover при доступности обоих серверов.
- Разрыв соединения во время `SELECT`.
- Разрыв соединения во время `INSERT`.
- Разрыв соединения во время `COMMIT`.
- Проверка поведения соединений, уже находящихся в пуле.
- Проверка отсутствия необходимости перезапуска Python-приложения.

## 7. Ожидаемый результат

Предложи минимально сложную, но надёжную production-архитектуру.

Мне не нужен PgBouncer, HAProxy или переход на Java. Желательно сохранить SQLAlchemy + asyncpg.

Прошу:

1. Проверить техническую корректность всех предположений.
2. Отделить возможности asyncpg от возможностей SQLAlchemy.
3. Объяснить, что уже работает автоматически, а что требует дополнительной реализации.
4. Предложить полный код подключения, проверки роли и восстановления соединений.
5. Показать правильное место для retry-логики.
6. Объяснить, нужно ли сохранять `@lru_cache`.
7. Предложить план локального тестирования перед единственным доступным production-развёртыванием.

**Главный приоритет — надёжность.** У меня практически одна возможность проверить решение в production, поэтому хочу максимально выявить ошибки и граничные сценарии локально.

Не утверждай, что переключение будет полностью бесшовным, если это не подтверждается реальными гарантиями драйвера, пула и PostgreSQL. Особенно внимательно проверь смену ролей двух живых серверов и поведение уже открытых соединений.


От себя добавлю одну важную вещь: не удаляй @lru_cache только потому, что другая модель назвала его проблемой. Кэширование объекта AsyncEngine само по себе не препятствует созданию новых физических соединений к другому Primary. Более того, бездумное пересоздание AsyncEngine на каждый запрос приведёт к потере преимуществ пула.

И ещё: полностью обезопасить систему одним механизмом подключения невозможно. Но можно сделать так, чтобы переключение происходило автоматически, а ошибки во время switchover обрабатывались предсказуемо, с ограниченным временем восстановления и без неконтролируемого повторения транзакций.
