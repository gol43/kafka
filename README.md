# AI Q-Score Analyzer

Сервис принимает очищенные диалоги из Data Cleaner, проверяет возможность анализа, сохраняет принятые данные в PostgreSQL и асинхронно формирует отчёт через GigaChat. Фронтенд получает уже подготовленные данные через восемь GET-ручек.

В этом README описаны:

- приём и анализ одного диалога;
- работа worker;
- конфигурация через ENV;
- контракт восьми GET-ручек;
- основные ошибки и граничные случаи.

Математика ежедневного построения dashboard здесь намеренно не рассматривается.

## 1. Основной поток анализа диалога

### 1.1. Вход от Data Cleaner

Data Cleaner вызывает:

```http
POST /api/v1.0/ai-q-score/internal/v1/dialogs/cleaned
```

Основные входные поля:

| Поле | Назначение |
|---|---|
| `call_id` | Уникальный идентификатор коммуникации |
| `manager_id` | Табельный номер менеджера: ровно восемь цифр |
| `client_epk` | Уникальный идентификатор клиента |
| `client_fio` | ФИО клиента; может отсутствовать |
| `duration_seconds` | Обязательная длительность звонка в секундах |
| `occurred_at` | Дата и время звонка |
| `cleaned_text` | Очищенный текст с понятными ролями сотрудника и клиента |
| `participants` | Участники коммуникации |
| `utterances` | Реплики с ролями и временными границами |
| `source_metadata` | Дополнительные данные источника |

Успешный HTTP-ответ — `202 Accepted`. Он означает, что callback обработан, но не гарантирует завершение анализа. Даже отфильтрованный диалог получает `202`; причина отражается в логах и метрике callback.

### 1.2. Проверки при приёме

Проверки выполняет `DialogIntakeService` в следующем порядке:

1. Проверяется переданная длительность.
2. Диалог короче `MIN_DIALOG_DURATION_SECONDS` отбрасывается и не сохраняется.
3. При включённом `CALENDAR_FILTER_ENABLED` определяется рабочая дата:
   - понедельник–четверг до 18:00 UTC — текущий день;
   - понедельник–четверг после 18:00 UTC — следующий календарный день;
   - пятница после 18:00 UTC — диалог отбрасывается;
   - суббота — диалог отбрасывается;
   - воскресенье после 18:00 UTC — назначается на понедельник;
   - воскресенье до 18:00 UTC — диалог отбрасывается.
4. `manager_id` должен находиться в `ANALYZED_MANAGER_IDS`.
5. Менеджеру должен быть назначен обязательный Prompt Analyzer.
6. Повторный `call_id` считается дубликатом и повторно не создаётся.
7. Принятый диалог и его задача сохраняются атомарно в PostgreSQL со статусом `waiting`.

Возможные внутренние результаты callback:

| Результат | Значение |
|---|---|
| `accepted` | Диалог и задача сохранены |
| `duration_filtered` | Диалог короче минимальной длительности |
| `calendar_filtered` | Диалог исключён календарной политикой |
| `manager_filtered` | Менеджер не входит в список анализируемых |
| `duplicate` | Такой `call_id` уже существует |

### 1.3. Персистентная очередь

Worker читает таблицу задач, а не держит очередь только в оперативной памяти. Поэтому рестарт приложения не теряет `waiting`-задачи.

Статусы:

| Статус | Значение |
|---|---|
| `waiting` | Ожидает worker |
| `processing` | Worker захватил задачу |
| `failed` | Один из обязательных этапов завершился ошибкой |
| `completed` | Отчёт успешно сохранён; завершённая задача удаляется |
| `not_analyzed` | Анализ не успел завершиться к окончательному cutoff 18:30 UTC |

Задачи захватываются через `FOR UPDATE SKIP LOCKED`. Несколько экземпляров worker не должны одновременно взять один и тот же диалог.

### 1.4. Работа worker

Worker:

1. Раз в `WORKER_POLL_INTERVAL_SECONDS` проверяет очередь.
2. Забирает не больше минимального значения между `WORKER_CLAIM_LIMIT` и `DIALOG_PIPELINE_CONCURRENCY`.
3. Ограничивает число одновременно исполняемых pipeline через `asyncio.Semaphore`.
4. Восстанавливает зависшие `processing`-задачи в `waiting`, если они старше `WORKER_STALE_TASK_SECONDS`.
5. Последовательно запускает назначенные диалогу обязательные анализаторы.
6. При любой ошибке обязательного анализатора помечает весь диалог и задачу как `failed`.
7. При успехе сохраняет готовый отчёт и удаляет завершённую задачу очереди.

В 18:00 UTC scheduler проверяет задачи текущего рабочего дня. Если существуют
`processing`-задачи, построение dashboard откладывается до 18:30 UTC. После
окончания grace period оставшиеся `waiting` и `processing` атомарно получают
`not_analyzed`, не попадают в dashboard и остаются в БД для последующего
контроля до истечения общего TTL. Поздний ответ GigaChat уже не может сохранить
отчёт поверх закрытого диалога.

`GIGACHAT_MAX_CONCURRENCY` — отдельный общий семафор именно HTTP-запросов в GigaChat. `DIALOG_PIPELINE_CONCURRENCY` ограничивает количество диалогов, одновременно проходящих весь pipeline. Эти ограничения решают разные задачи.

### 1.5. Три независимых Prompt-анализа

Для каждого диалога выполняются три логически независимых запроса в GigaChat:

1. **Hygiene** — общие правила коммуникации.
2. **Deposit** — критерии вкладов и техническая метрика `DEPOSIT_TOPIC`.
3. **Risk** — клиентские риски.

Каждый критерий возвращает бинарный `score`:

- `1` — критерий выполнен, риск не выявлен;
- `0` — критерий нарушен или риск выявлен.

`DEPOSIT_TOPIC` используется только как технический gate:

- анализируется и сохраняется;
- определяет, применимы ли остальные критерии вкладов;
- не должен появляться ни в одном UI-ответе благодаря `UI_HIDDEN_METRIC_CODES`.

Если тема вкладов не подтверждена, остальные депозитные результаты не участвуют в Q-score и аналитике метрик. Risk-анализ не влияет на Q-score.

### 1.6. Успешный результат

После успешного pipeline сохраняются:

- исходные идентификаторы и очищенный текст;
- результаты Hygiene;
- результаты Deposit;
- результаты Risk;
- отдельные оценки Hygiene, Deposit и итоговая оценка диалога;
- флаг темы вкладов;
- число отклонений и рисков;
- полностью подготовленный payload детального отчёта;
- версии модели, критериев и промптов;
- срок удаления согласно `DATA_TTL_DAYS`.

GET-ручки никогда не запускают GigaChat и не пересобирают текст отчёта. Они читают готовые данные из PostgreSQL.

## 3. Восемь GET-запросов

Все `manager_id` нормализуются до восьми цифр. Значение должно состоять только из цифр и содержать не больше восьми символов. API читает последний сформированный snapshot; дата от фронтенда для dashboard-блоков не требуется.

### 3.1. Q-score

```http
GET /api/v1.0/ai-q-score/manager/{manager_id}/q-score
```

Возвращает:

```json
{
  "personal": 84.0,
  "teamMedian": 81,
  "months": [
    {"year": 2026, "month": 11, "qScore": 84},
    {"year": 2026, "month": 10, "qScore": 82},
    {"year": 2026, "month": 9, "qScore": 0},
    {"year": 2026, "month": 8, "qScore": 0}
  ]
}
```

Критические случаи:

- неверный `manager_id` — `400`;
- snapshot отсутствует — `404`;
- история месяца отсутствует — возвращается `qScore: 0`, а не `null`;
- всегда возвращаются четыре месяца, включая текущий.

### 3.2. Клиенты в зоне риска

```http
GET /api/v1.0/ai-q-score/manager/{manager_id}/client-risks
```

Возвращает список клиентов:

```json
{
  "items": [
    {
      "clientEpk": "10000001",
      "clientFio": "Иванов Иван Иванович",
      "level": "high"
    }
  ]
}
```

У клиента может быть несколько рисков, но в списке клиент присутствует один раз. Его уровень равен максимальному уровню найденных рисков: `high` выше `medium`, `medium` выше `low`. Сортировка: сначала уровень риска, затем фамилия клиента по алфавиту, затем EPK.

Критические случаи:

- рисков нет — `items: []`;
- ФИО отсутствует — `clientFio: ""`, такие записи идут после клиентов с ФИО внутри уровня;
- snapshot отсутствует — `404`.

### 3.3. Подробности рисков клиента

```http
GET /api/v1.0/ai-q-score/manager/{manager_id}/client-risks/{client_epk}
```

Возвращает клиента и все его разные риски:

```json
{
  "clientEpk": "10000001",
  "clientFio": "Иванов Иван Иванович",
  "level": "high",
  "risks": [
    {
      "metricCode": "RISK_01",
      "title": "Намерение прекратить обслуживание",
      "level": "high",
      "quote": "Тогда я ухожу из банка",
      "count": 2,
      "recommendation": "..."
    }
  ]
}
```

`count` — количество уникальных звонков клиента, где выявлен конкретный риск. Цитата и ФИО берутся из последнего по времени случая соответствующего риска. Уровень клиента — максимальный среди его рисков.

Хранение ФИО управляется `ENCRYPT_CLIENT_FIO_AT_REST`. При `true` ФИО остаётся зашифрованным в `dialogs`, `dialog_reports`, дневных агрегатах, snapshots и сохранённом payload; API расшифровывает его непосредственно перед ответом. Сортировка риска по фамилии использует расшифрованное значение только в памяти расчёта. Изменение колонок оформляется штатной Alembic-ревизией рабочего проекта.

Критические случаи:

- клиент или его риск не найден в последнем snapshot — `404`;
- цитата отсутствует — пустая строка;
- один и тот же риск в нескольких звонках агрегируется в один объект.

### 3.4. Strengths — «Получается отлично»

```http
GET /api/v1.0/ai-q-score/manager/{manager_id}/strengths
```

Возвращает:

```json
{
  "items": [
    {
      "metricCode": "HYG_02",
      "title": "Приветствие",
      "percent1": 95,
      "percent2": 90,
      "delta": "+5"
    }
  ]
}
```

`title` формируется из `title_positive`. `UI_HIDDEN_METRIC_CODES` не возвращаются нигде. `STRENGTHS_EXCLUDED_METRIC_CODES` исключаются только из этого топа.

Критические случаи:

- подходящих метрик нет — `items: []`;
- недостаточная выборка — метрика не показывается;
- snapshot отсутствует — `404`.

### 3.5. Improvements — «Нужно улучшить»

```http
GET /api/v1.0/ai-q-score/manager/{manager_id}/improvements
```

Возвращает:

```json
{
  "items": [
    {
      "metricCode": "HYG_15",
      "title": "Разговор не завершён корректно",
      "percent1": 40,
      "percent2": 30,
      "delta": "+10"
    }
  ]
}
```

Процент здесь является долей нарушений: `0%` — нарушений не было, `100%` — нарушение было во всех учитываемых коммуникациях. `title` формируется из `title_negative`. Рекомендация в основной карточке намеренно не возвращается.

Критические случаи аналогичны Strengths.

### 3.6. Подробности конкретной Improvement-метрики

```http
GET /api/v1.0/ai-q-score/manager/{manager_id}/improvements/{metric_code}
```

Возвращает:

```json
{
  "metricCode": "HYG_15",
  "title": "Разговор не завершён корректно",
  "recommendation": "...",
  "severity": "significant",
  "periods": [
    {
      "periodStart": "2026-11-02",
      "periodEnd": "2026-11-08",
      "percent": 40
    }
  ],
  "communications": [
    {
      "callId": "call-001",
      "type": "call",
      "clientEpk": "10000001",
      "clientFio": "Иванов Иван Иванович",
      "occurredAt": "2026-11-06T12:00:00Z"
    }
  ]
}
```

В `periods` остаются только начало, конец и процент завершённой недели. Текущая незавершённая неделя не возвращается. В коммуникациях нет цитаты.

Критические случаи:

- метрика не вошла в Improvements последнего snapshot — `404`;
- завершённых недель нет — `periods: []`;
- нарушающих коммуникаций нет — `communications: []`.

### 3.7. Список коммуникаций

```http
GET /api/v1.0/ai-q-score/manager/{manager_id}/dialogs
```

Параметры:

| Параметр | Тип | Значение |
|---|---|---|
| `score` | string | Зона оценки: `low`, `medium` или `high` |
| `client_epk` | string | Точное совпадение EPK клиента |
| `date_from` | date | Начало периода включительно, формат `YYYY-MM-DD` |
| `date_to` | date | Конец периода включительно, формат `YYYY-MM-DD` |
| `offset` | integer | Смещение, по умолчанию `0` |
| `limit` | integer | Размер страницы; default из `LATEST_COMMUNICATIONS_LIMIT`, максимум из `COMMUNICATIONS_MAX_LIMIT` |

Зоны `score`:

| Значение | Условие | Смысл |
|---|---:|---|
| `low` | `score <= 40` | Низкая оценка диалога |
| `medium` | `41 <= score <= 79` | Средняя оценка диалога |
| `high` | `score >= 80` | Высокая оценка диалога |

Пример:

```http
GET /api/v1.0/ai-q-score/manager/00000001/dialogs?score=medium&client_epk=10000001&date_from=2026-10-01&date_to=2026-11-06&offset=0&limit=20
```

Фильтры объединяются через логическое AND. Результат сортируется по `occurredAt` от нового к старому. Возвращаются только готовые отчёты не позднее рабочей даты последнего snapshot менеджера.

Ответ:

```json
{
  "items": [
    {
      "callId": "call-001",
      "type": "call",
      "clientEpk": "10000001",
      "occurredAt": "2026-11-06T12:00:00Z",
      "score": 72
    }
  ],
  "hasMore": false
}
```

Критические случаи:

- dashboard менеджера ещё не сформирован — `404`;
- `limit` больше разрешённого — `400`;
- `offset < 0` или `limit < 1` — `422`;
- неверный формат даты — `422`;
- неизвестное значение `score` — `422`; разрешены только `low`, `medium`, `high`;
- `date_from > date_to` даёт пустой результат;
- совпадений нет — `items: []`, `hasMore: false`;
- `hasMore: true` означает, что существует следующая страница;
- отдельного фильтра по ФИО клиента и типу коммуникации в текущем API нет;
- `client_epk` — точное совпадение, не поиск по части строки.

### 3.8. Отчёт одного диалога

```http
GET /api/v1.0/ai-q-score/manager/dialogs/{call_id}
```

Ответ:

```json
{
  "callId": "call-001",
  "clientEpk": "10000001",
  "clientFio": "Иванов Иван Иванович",
  "occurredAt": "2026-11-06T12:00:00Z",
  "type": "call",
  "score": 72.0,
  "deviationsCount": 3,
  "risks": [
    {
      "code": "RISK_01",
      "title": "Намерение прекратить обслуживание",
      "severity": "high"
    }
  ],
  "strengths": "Вы хорошо выполнили следующие критерии: ...",
  "improvements": [
    {
      "code": "HYG_15",
      "title": "Разговор не завершён корректно",
      "severity": "significant",
      "recommendation": "...",
      "quote": "..."
    }
  ]
}
```

В `risks` попадают только выявленные риски с `score = 0`. Strengths-текст создаётся один раз при сохранении анализа и не меняется между GET-запросами. Технические метрики из `UI_HIDDEN_METRIC_CODES`, включая `DEPOSIT_TOPIC`, отсутствуют в Strengths и Improvements.

Критические случаи:

- `call_id` не найден — `404`;
- анализ ещё не завершён или готовый payload не сформирован — `404`;
- ФИО или цитата отсутствуют — пустая строка;
- `waiting`, `processing`, `failed` и `not_analyzed` наружу не возвращаются;
- повторный GET возвращает сохранённый результат и не запускает GigaChat.

## 4. Общие правила API

- В UI-ответах не должно быть `null`: отсутствующая строка превращается в `""`, отсутствующий список — в `[]`, числовые значения формируются как `0` или `0.0`.
- Dashboard GET читает последний готовый snapshot менеджера.
- Детальный отчёт читает готовый результат по `call_id`.
- API не выполняет тяжёлую агрегацию и не вызывает LLM во время GET.
- `DEPOSIT_TOPIC` остаётся внутренней технической метрикой и не показывается фронтенду.
