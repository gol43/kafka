Скажу, что другая нейросеть допустила серьёзную техническую ошибку, но при этом правильно обозначила несколько реальных проблем с failover.

Главное: утверждение, что `asyncpg 0.31.0` не поддерживает несколько PostgreSQL-хостов, неверно.

Здесь нужно различать три уровня:a

1. asyncpg — умеет принимать несколько хостов и выбирать сервер по `target_session_attrs`.
2. SQLAlchemy 2.0.51 — поддерживает передачу нескольких хостов драйверу asyncpg.
3. SQLAlchemy QueuePool — повторно использует уже открытые соединения и сам по себе не гарантирует обнаружения смены роли живого PostgreSQL.

Именно третий пункт создаёт настоящую проблему.

## 1. Доказательство из официальной документации

Я проверил документацию самих разработчиков, а не ответы других моделей.

SQLAlchemy прямо документирует multihost для asyncpg:

```
engine = create_async_engine(    "postgresql+asyncpg://user:password@/dbname"    "?host=HostA:5432"    "&host=HostB:5432")
```

Эта возможность появилась в SQLAlchemy 2.0.18, а у тебя 2.0.51.&#x20;

## 2. Что другая нейросеть предлагает неправильно

| Утверждение                                                | Моя оценка               |
| ---------------------------------------------------------- | ------------------------ |
| asyncpg не поддерживает multihost                          | &#x20;Неверно            |
| Нужно сохранить `master_host_and_port`                     | &#x20;Необязательно      |
| Нужно удалить `lru_cache`                                  | &#x20;Не требуется       |
| `pool_pre_ping` обнаружит мёртвые соединения               | &#x20;Да, при checkout   |
| При смене ролей живые соединения могут остаться на Standby | &#x20;Верно              |
| Нужна проверка роли при checkout                           | &#x20;Подходящий вариант |
| После каждого failover обязательно пересоздавать Engine    | &#x20;Нет                |

Есть ещё одна проблема с предложением другой модели: `engine.dispose()` не изменяет DSN существующего Engine.

Если Engine был создан с единственным адресом `host1`, то после `dispose()` он продолжит создавать соединения к `host1`.

Поэтому идея «вызвать dispose, заново определить мастер и автоматически получить новый DSN» не работает без отдельного механизма замены Engine.

А если Engine изначально создан с двумя хостами, заново определять мастер самостоятельно не нужно.

## 3. Какую архитектуру я предлагаю в итоге

Я бы оставил твою существующую структуру:

```
@lru_cachedef get_database_engine() -> AsyncEngine:    return create_async_engine(...)
```

И реализовал три механизма:

1. Multihost DSN + `target_session_attrs="read-write"`

   При создании нового физического соединения asyncpg самостоятельно ищет подходящий сервер.
2. Проверка роли PostgreSQL при checkout

   При выдаче соединения из пула проверяем, не стал ли сервер Standby. Если стал — инвалидируем соединение и заставляем пул создать новое.
3. Retry на уровне бизнес-операции

   Если failover произошёл посреди транзакции, создаём новую сессию и повторяем только безопасные операции. Для операций с неопределённым результатом COMMIT требуется отдельная защита от дублей.

Но здесь есть техническая тонкость: при обнаружении Standby недостаточно инвалидировать только одно соединение. Остальные соединения пула тоже могут вести на бывший Primary. Поэтому механизм инвалидации нужно спроектировать так, чтобы они также были перепроверены или заменены.

## 4. Что действительно важно перед production

Тебе нужна не просто правильная строка подключения, а проверяемое поведение при реальном switchover.

Я бы считал решение готовым только после успешного прохождения трёх тестов:

- Тест A: Primary полностью недоступен. Приложение находит новый Primary и продолжает работать.
- Тест B: оба сервера живы, но роли поменялись. Приложение перестаёт использовать старые соединения для записи и переходит на новый Primary.
- Тест C: переключение происходит посреди транзакции. Приложение корректно обрабатывает ошибку, не создавая дублирующих записей.

Именно тест B является ключевым для твоей задачи.

Итог: менять драйвер, отказываться от `lru_cache`, сохранять ручной поиск Primary или добавлять PgBouncer не требуется. Текущий стек поддерживает нужную основу.

Однако пока мы не реализовали и не протестировали проверку роли при checkout и восстановление транзакций, называть решение production-ready нельзя.
