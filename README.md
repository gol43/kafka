### 1. asyncpg не выбирает Primary только при первом запуске приложения

Это неточная формулировка.

`asyncpg` выбирает подходящий хост при создании каждого нового физического соединения, а не только при первом вызове `create_async_engine()`.

У тебя:

```
pool_size=10max_overflow=20pool_pre_ping=True
```

SQLAlchemy создаёт и переиспользует физические соединения в пуле.

Представим ситуацию:

1. В пуле находятся 10 соединений к `postgres-1`.
2. `postgres-1` падает.
3. SQLAlchemy пытается выдать соединение из пула.
4. `pool_pre_ping=True` обнаруживает, что соединение разорвано.
5. SQLAlchemy инвалидирует устаревшие соединения и создаёт новое.
6. `asyncpg` перебирает хосты из DSN и находит новый Primary.

Для этого вручную вызывать `engine.dispose()` обычно не требуется.

Но есть нюанс: `pool_pre_ping` работает при выдаче соединения из пула, а не во время выполнения SQL-запроса.

### 2. Что произойдёт, если Primary упадёт во время транзакции?

Предположим:

```
async with session_maker() as session:    async with session.begin():        await session.execute(...)
```

В момент `execute()` сервер становится недоступным.

Тогда:

- SQLAlchemy получает ошибку соединения.
- Если ошибка распознана как disconnect, соединение инвалидируется.
- Текущая транзакция прерывается.
- Сам SQL-запрос автоматически не повторяется.
- Для повторной попытки требуется новая транзакция и, как правило, новая сессия.

Именно здесь нужна retry-логика.

Причём нельзя просто перехватить любой `ConnectionError` и повторить запрос: необходимо учитывать ошибки `DBAPIError`, признак `connection_invalidated` и неопределённость результата `COMMIT`.

### 3. А действительно ли Java JDBC лучше?

Нет, в этом отношении принципиального преимущества нет.

JDBC PostgreSQL тоже не переносит уже выполняющуюся транзакцию на другой сервер после его отказа.

Он умеет выбрать подходящий хост при установлении нового соединения. Но существующее соединение при отказе Primary также может завершиться ошибкой.

В Spring дополнительную обработку могут обеспечивать пул HikariCP и retry-механизмы приложения, например Spring Retry. Сам JDBC не гарантирует бесшовного повтора транзакций.

Во втором случае `pool_pre_ping=True` сам по себе недостаточен, потому что он проверяет доступность соединения, а не роль PostgreSQL.
Тогда задача понятна. Тебе нужен автоматический failover при смене ролей PostgreSQL Primary ↔ Standby, причём оба сервера могут оставаться доступными, а Python-приложение не должно перезапускаться.

И здесь есть один важный нюанс: `pool_pre_ping=True` недостаточно.

### Почему?

Представим:

1. `postgres-1` — Primary, `postgres-2` — Standby.
2. SQLAlchemy создал 10 соединений к `postgres-1`.
3. Инфраструктура переключила роли: `postgres-1` стал Standby, `postgres-2` стал Primary.
4. Все 10 соединений к `postgres-1` остались живыми.
5. `pool_pre_ping=True` проверяет соединение — PostgreSQL отвечает.
6. SQLAlchemy продолжает использовать старый сервер, который теперь доступен только для чтения.

В результате `SELECT` работает, а `INSERT` или `UPDATE` завершается ошибкой `ReadOnlySQLTransaction`.

### Что я рекомендую

Оставляем твои `SQLAlchemy + asyncpg`, multihost DSN и `target_session_attrs="read-write"`.

Но добавляем механизм, который при обнаружении смены роли заставляет SQLAlchemy отказаться от старых соединений и создать новые.

Например, на уровне `AsyncEngine`:

```
engine = create_async_engine(    multihost_dsn,    pool_size=10,    max_overflow=20,    pool_pre_ping=True,    connect_args={        "target_session_attrs": "read-write",        "statement_cache_size": 0,        "timeout": 5,    },)
```

И при обнаружении, что соединение попало на бывший Primary, выполняем:

```
await engine.dispose()
```

После этого новые соединения будут создаваться через asyncpg, который заново выберет сервер, принимающий запись.

Но `dispose()` сам по себе не обнаруживает смену ролей. Нужен триггер: ошибка записи в read-only транзакции либо проверка роли сервера при получении соединения.

| Подход                                             | Преимущество                           | Недостаток                                    |
| -------------------------------------------------- | -------------------------------------- | --------------------------------------------- |
| Проверять роль при каждом получении соединения     | Можно обнаружить смену роли до записи  | Дополнительный SQL-запрос при каждом checkout |

При этом можно сделать почти то, что ты хочешь, с минимальным количеством кода:

2. В `connect_args` задаёшь `target_session_attrs="read-write"`.
3. При выдаче соединения из пула проверяется, что сервер всё ещё Primary.

Это работает во время жизни приложения, а не только при запуске.

Если хочешь именно без дополнительного Python-кода, то надёжный вариант — подключение через HAProxy/кластерный endpoint, который направляет новые соединения на актуальный Primary и закрывает старые при смене роли.

Тогда Python получает один адрес:

